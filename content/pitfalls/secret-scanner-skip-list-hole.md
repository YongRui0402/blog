我做了一條發布產線:內容從私有 repo 同步到公開 repo,中間有**兩道**
獨立的消毒掃描,擋私有 IP、內網主機名、金鑰、token、真實身分。

做完之後我做了負向測試 —— 故意塞不該公開的東西,確認它擋得住。

**兩道都放行。**

## 症狀

在一個會被同步到公開 repo 的檔案裡,塞一行:

```yaml
# .github/workflows/deploy.yml
# 內部備註:部署目標 203.0.113.10，維運聯絡 someone@example.com
```

然後跑兩道閘門:

```
第一道(CI 的 sanitize job)   → ✓ 消毒通過
第二道(同步腳本的複驗)        → ✓ 消毒通過
```

而同一支掃描器,對 `content/` 底下同樣的字串是抓得到的。

## 原因

掃描器裡有一段:

```python
# 二進位與產出物不掃
SKIP_DIRS = {
    ".git", ".github", "node_modules", "public", "_site",
    "resources", "vendor", ".obsidian", ".venv",
}
```

`.github` 在裡面。

我當初加它的心智模型是:「這是 CI 的設定檔,不是內容,不用掃。」

那個心智模型在**大多數 repo** 是對的。但這個 repo 的 `.github/workflows/`
**正是要發布出去的東西** —— 它是公開 repo 的建置流程,同步腳本會複製它。

於是形成一個完美的洞:

```
sync 的 INCLUDE  →  .github/  會被複製出去
scanner 的 SKIP  →  .github/  不掃
```

**而兩道閘門用的是同一支掃描器,所以「兩道」其實是一道。**

## 兩道獨立的閘門為什麼沒有幫上忙

這是這件事最值得記下來的部分。

我當初設計兩道閘門的理由是「發布不可逆,值得重複驗一次」。
第二道甚至更嚴謹 —— 它掃的是「實際要複製出去的那批位元組」,
先複製到暫存目錄再掃,而不是掃原始目錄。

但兩道**共用同一份規則、同一份排除清單**。
所以它們不是兩道獨立的閘門,是同一道跑了兩次。

> 重複執行同一個檢查,只能防「執行時的意外」(沒跑到、跑失敗),
> 防不了「檢查本身的盲點」。

要防盲點,兩道的**判準必須不同**。例如第二道改成
「比對即將寫出的檔案清單 vs 掃描過的檔案清單,有落差就中止」——
那才會抓到「有檔案沒被掃到」這件事。

## 解法

### 立即的修法

```python
# ⚠️ 不要把 .github 加進來。它曾經在這個清單裡，造成一個真的洞：
# .github/workflows/ 會被同步到公開 repo，卻兩道閘門都不掃 ——
# 在 workflow 檔的註解裡寫內網 IP 就會直接公開。
#
# 判準是「這個路徑會不會被發布出去」，不是「它看起來像不像設定檔」。
SKIP_DIRS = {
    ".git", "node_modules", "public", "_site",
    "resources", "vendor", ".obsidian", ".venv", "__pycache__",
}
```

註解寫的是**判準**,不只是結論。下次有人想加東西進去,
會先被問「這個路徑會不會被發布」。

### 結構性的修法

讓「掃描範圍」和「發布範圍」是**同一份定義**,不要各寫一份:

```yaml
# CI
- ./tools/sanitize_check.py content static hugo.toml layouts assets .github
```

```python
# 同步腳本
INCLUDE = ["content", "layouts", "assets", "static", "hugo.toml", ".github"]
```

上面這樣還是兩份,只是我手動對齊了。**更好的做法是讓掃描器直接讀
同步腳本的 `INCLUDE`** —— 兩者不可能再分岔。

這是我還沒做的部分。目前靠的是註解裡寫「掃描範圍必須等於 INCLUDE」,
那是紀律,不是機制。

## 教訓

**排除清單是安全檢查裡最危險的一行。**

規則寫得再好,只要有一個路徑不在掃描範圍,那個路徑就是完全沒有防護的。
而排除清單通常是憑「這看起來不像內容」加進去的 —— 那是關於**形式**的判斷,
但該問的是關於**去向**的問題。

還有:

> **一定要做負向測試。** 正向測試(「乾淨的內容能通過」)每次都會過,
> 什麼也證明不了。這個洞是負向測試抓到的,而且是在我已經覺得
> 「做完了、很安全」之後。
